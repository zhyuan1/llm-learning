# 编排、仲裁、汇聚、回滚：多 Agent 系统的四个工程难题

单 Agent 跑不动复杂任务，原因很清楚：上下文窗口有上限，工具太多会误选，有些任务天然可以并行但单线程跑不了。多 Agent
系统是合理的出路——但它把原来的一个执行单元变成了一个分布式系统。分布式系统带来的经典问题，多 Agent 系统一个也没绕过。

四个问题：**编排**（谁做什么）、**仲裁**（有分歧怎么办）、**汇聚**（结果怎么合并）、**回滚**（出错了怎么办）。

---

## 一、编排：分解本身是一道推理题

编排（Orchestration）解决的问题是：一个大任务，怎么拆，拆给谁。

直觉上这像是一个路由问题，写一个 `if-else` 或者一张规则表就能解决。实际上不是。

Rasal 和 Hauer 在 2024 年的研究（arXiv:2402.16713）做了一个简单实验：让 GPT-3.5 直接解 GSM8K 数学题，正确率
50%。换一个架构——用一个"编排 LLM"先把题目分解成子问题，再分配给专门的 Agent 解决——正确率升到了 73%。模型权重没变，升了 23
个百分点。这 23 个点全部来自分解本身。

分解是一个推理任务，不是规则匹配。编排层需要理解任务的语义，判断哪些子任务可以并行、哪些必须串行，以及在任务边界不清楚时先向上游问清楚再拆分。

### 三种拓扑，三种代价

**顺序型（Pipeline）**：Agent A 完成后把结果传给 Agent B，B 传给 C。最可预测，最容易调试，成本可估算。代价是延迟线性累积——如果每步平均
10 秒，10 步就是 100 秒。

**并行型（Concurrent/Swarm）**：多个 Agent 同时处理不同子任务。延迟变成了"最慢的那个"而不是"所有的加总"
。代价是需要解决结果汇聚（第三节），而且并发 API 调用会带来成本峰值。

**层级型（Hierarchical）**：一个 Lead Agent 把任务分给 Team Agent，Team Agent 再分给 Worker Agent。适合 20+ Agent
的大规模场景，因为每一层都压缩了上层需要管理的复杂度。代价是双重的：延迟在每一层叠加，信息在每一层被摘要——顶层 Lead Agent
看到的不是原始执行结果，是经过多次压缩的摘要。

### 被忽视的瓶颈：工具集大小

编排的讨论通常集中在"分给谁"，但有一个更隐蔽的问题：每个 Agent 能看见什么工具。

对 Llama 3.1 405B 的测试显示：工具数量超过 30 个后，模型开始出现工具误选和参数错误。改为动态加载——根据任务类型为每个 Agent
只暴露 Top 5-10 个工具——准确率提升约 30%。

所以编排层的职责不只是任务分配，还包括上下文管理：决定每个子 Agent 在执行时能看见哪些工具、哪些历史信息。分配策略设计得再好，如果每个
Agent 的工具集是全量的，下游仍然会跑坏。

## 二、仲裁：两个 Agent 结论不同，听谁的

仲裁（Arbitration）解决的是：多 Agent 并行工作时，如果它们的结论互相矛盾，以谁为准。

在分布式系统里，这个问题有一个著名的表述——拜占庭将军问题：如果网络里有恶意节点，怎么让其余节点达成一致？有研究者把这个框架套用到了
LLM Agent 系统，结论是 LLM Agent 比传统代理更"多疑"，在遭受恶意信息攻击时表现更好。CP-WBFT 协议在 85.7%
的节点是恶意节点的极端条件下，仍然维持了 100% 的最终准确率（arXiv:2511.10400）。

但这个场景在实际工程里并不常见。更普遍的情况是：**两个 Agent 都是善意的，但得出了不同的结论**。一个调用了旧的 API
文档，另一个爬取了最新网页；一个强调保守，另一个强调效率。没有人在撒谎，但结论不同。这类语义冲突无法用拜占庭协议解决，因为协议的假设前提是存在一个"
正确答案"，而语义冲突里双方可能都对。

### 三层分级

zylos.ai 的研究给出了一个实用的数据点：未解决的冲突导致 30% 的性能下降（表现为输出质量下滑、任务卡住、或 Agent 在相互等待中循环）。

分级处理比一刀切有效：

- **低风险冲突**（格式选择、措辞偏好）：优先级规则。静态，快，不需要推理。
- **中风险冲突**（策略选择、方案取舍）：强化学习议价框架，自动化处理 70-80% 的冲突。
- **高风险冲突**（涉及真实世界操作，或结论影响重大的判断）：人工审核，不可省略。

这个分级和 Anthropic 指南里的"Evaluator-Optimizer"模式呼应——专设一个 Critic Agent 作为裁判，负责评估其他 Agent
的输出，在产生分歧时触发仲裁流程。

### 辩论的失效条件

让 Agent 互相辩论，真理越辩越明——这在某些条件下是对的，但有一个重要的失效模式。

Du 等人（arXiv:2305.14325）发现：当参与辩论的模型能力相近、或者初始答案相近时，辩论过程会收敛到多数意见，而不是正确答案。几个模型互相说服，最终大家都选了同一个错误答案——而且谁都觉得自己是被说服的，不是被压制的。

辩论需要多样性作为前提。让三个同款 GPT-4 辩论，效果可能不如让 GPT-4、Claude、Gemini 各自独立回答然后投票。仲裁机制的选择取决于两个维度：冲突的风险等级，以及参与的
Agent 是否具有真实的多样性。

## 三、汇聚：结果来了，如何合成

汇聚（Aggregation）解决的是：多个 Agent 分别完成了任务，怎么把它们的输出合并成一个一致的、高质量的最终答案。

和仲裁的区别：仲裁处理的是"结论矛盾"；汇聚处理的是"结论并不矛盾，但各说各的，需要综合"。比如三个 Agent 分别研究了竞争对手的产品
A、B、C，现在要生成一份综合报告。

### 四种方法的能力边界

**多数投票（Majority Voting）**：多个 Agent 各自独立给出答案，票数最多的胜出。实现零成本，但"对的少数"会被压制——三个 Agent
里有两个错的，正确答案直接被淘汰。

**加权共识（Weighted Consensus）**：根据每个 Agent 的置信度或历史准确率加权。效果比多数投票好，但需要可靠的质量信号，而模型自报的置信度往往过度自信，不等于真实准确率。

**多 Agent 辩论（Multi-Agent Debate）**：迭代细化，Agent 们互相看到对方的推理过程后修改自己的答案。质量上限高，但成本是 O(n ×
rounds)，同质模型仍有收敛到多数意见的风险（见第二节）。

**混合专家架构（Mixture of Agents, MoA）**：层级汇聚。第一层多个"提案 Agent"各自独立生成答案；第二层"汇聚 Agent"
把所有提案作为上下文，重新生成一个综合答案；可以有多层。

### MoA 的核心发现

Wang 等人在 2024 年（arXiv:2406.04692）做了一个反直觉的实验：把一个更弱模型的答案作为参考，给一个更强模型看，强模型的输出反而更好了。

这不是平均，也不是投票。当一个 LLM 能看到其他模型的推理轨迹时，它会重新审视自己的思路，触发更全面的推理。论文把这个现象叫做"
collaborativeness"（协作性）。最终结果：MoA 只用开源模型，在 AlpacaEval 2.0 上达到 65.1% 的胜率，超过了 GPT-4 Omni 的 57.5%。

### 层级汇聚的信息损耗

层级型架构有一个系统性弱点：每一层汇聚都会压缩信息。

一个 Worker Agent 产出了 2000 字的分析，Team Agent 把它压缩成 200 字的摘要传给 Lead Agent，Lead Agent 再基于 200 字做决策。丢掉的那
1800 字里，可能有关键的异常情况、反例、或者置信度标注，而 Lead Agent 永远不会知道。这和 Agent 长任务里的"上下文锁定"
是同一个机制——模型基于不完整的信息形成了固化的判断，后续反驳信息无法穿透已经形成的结论。

选择汇聚方式的关键问题是：能否拿到可靠的质量信号？有质量信号，用加权共识；没有，用 MoA（让模型自己判断哪个参考更有用）；Agent
之间真的多样，再考虑辩论。

## 四、回滚：出错了，能退到哪

回滚（Rollback）解决的是：Agent 在执行中出了错，如何安全地恢复到一个好状态继续执行。

这是四个难题里最容易被推迟处理的一个。在开发阶段，失败了就重跑整个 pipeline，没什么代价。在生产环境里，一个长任务执行到一半失败意味着前面的
API 调用、工具执行、甚至真实世界操作都已经发生了——"重跑"没有意义。

### 三种回滚语义

LangGraph 的状态管理设计（activewizards.com）把回滚分成三种语义：

**直接续跑（Straight Resume）**：每次执行的状态都被保存为 Checkpoint。如果某个节点失败，重新调用时从最后一个成功的 Checkpoint
继续，不重复已完成的步骤。适合失败原因是外部的（网络超时、API 限流），而不是逻辑错误。

**修改后重跑（Replay with Modification）**：用 `graph.update_state()` 修改历史 Checkpoint
的某个字段，然后重新执行。适合某个中间节点的输出质量很差，想在不重跑前面步骤的情况下修正它再继续。LangGraph 把这个叫做"time
travel"——可以回到任意一个历史节点，修改它，再从那个节点向前执行。

**线程隔离（Thread Isolation）**：每个 `thread_id` 是独立的执行上下文。某条线程失败，不污染其他线程的状态。对于 1000 个 Agent
并行的场景，这是基础设施层面的隔离保证。

LangGraph Cloud 还支持一个额外的策略：当新的用户输入到达一个正在执行中的线程时，可以直接**回滚当前执行**
，从头开始处理新的输入，适合实时对话场景。

### 软回滚：Reflexion 模式

Shinn 等人（arXiv:2303.11366）提出了一种不依赖基础设施的回滚——Reflexion。

Agent 执行失败后，不重跑，而是先生成一段对失败原因的自然语言反思（"我在第三步用了错误的搜索关键词，导致没有找到相关论文"
），把这段反思存入情节记忆（episodic memory），下一次尝试时把这段反思作为上下文输入，让模型带着对过去错误的认知重新执行。

HumanEval 编码基准上：直接重跑是 67%，Reflexion 后是 91%。这是一种认知层的回滚——不回滚执行状态，而是更新认知状态。在错误原因复杂、需要推理失败模式的场景下，比无脑重跑更有效。

### 不可逆操作的边界

有些操作无法回滚：发送的邮件、已提交的支付、删除的数据库记录、向外部系统 POST 的请求。

对于这类操作，正确的处理位置是**执行之前**，而不是执行之后——在不可逆操作节点之前强制插入"人工批准检查点"（Human-in-the-Loop
Gate）。Anthropic 的指南和 Nick Gupta 的生产实践都指向同一个结论：这是架构决策，不是错误处理。一个没有在设计阶段标注出不可逆操作节点的
Agent 系统，在生产环境中只是还没出错而已。

## 四个难题的系统关系

这四个问题覆盖了 Agent 执行生命周期的不同阶段：

- **编排**：任务开始时，大目标怎么变成可执行的子任务
- **仲裁**：执行中，冲突怎么解决，谁有决策权
- **汇聚**：执行结束时，各自的产出怎么合并成最终答案
- **回滚**：出错时，失败了怎么安全地恢复

四个问题互相不独立。编排设计得不好（拓扑选错、工具集太大），下游的仲裁和汇聚问题会放大。汇聚机制设计得不好（层级压缩），给编排层提供的反馈质量就会下降。回滚如果没有
Checkpoint 支持，出错就只能从头跑，而从头跑又意味着要重新触发编排、仲裁、汇聚的整个过程。

一个最小可生产多 Agent 系统的设计清单：

- [ ] 编排层有明确的分解逻辑，支持动态工具集（不是把所有工具塞给每个 Agent）
- [ ] 高风险操作节点有人工批准检查点
- [ ] 所有节点有 Checkpoint 持久化，支持失败后从断点恢复
- [ ] Critic Agent 或汇聚层有质量验证步骤
- [ ] 有可观测性（每个 Agent 的决策轨迹可查）

还有两个问题这篇文章没有解决：

**成本控制**：并行型和层级型架构在规模扩大时，API 调用成本以非线性速度增长。Kimi K2.6 支持 1000 个 Agent 并行，但 1000 个并发
LLM 调用的成本是多少，谁来控制预算上限，目前仍是开放问题。

**调试的可观测性**：单 Agent 失败好排查；多 Agent 失败很难排查——失败可能是编排层分解错误、某个中间 Agent
输出质量差、或汇聚层的信息压缩丢失了关键信息，三者在外部表现几乎一样。企业级可观测性（LangGraph、Agent 365、Anthropic Managed
Agents 全都在强调这一点）是 2026 年多 Agent 系统落地的最大瓶颈，不是算法能力。
