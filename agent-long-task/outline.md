# 文章大纲：AI Agent 为什么跑着跑着就不对了

目标读者：对 AI Agent 落地感兴趣的开发者、产品经理、技术作者
字数目标：7000 字左右
风格：有论据、有数据、有反直觉洞察，不煽情

---

## 一、开头：一个反常识的数据（引入）

- TravelPlanner benchmark：GPT-4 成功率 0.6%（1225 个任务）
- 这不是 GPT-4 不够聪明，而是任务本身需要在长上下文里同时追踪多个约束
- 来源：S2

**写作目标**：用一个让人怀疑自己没看错的数字打开，建立"这不是你以为的那个问题"的悬念

---

## 二、不只是 TravelPlanner 的问题

- UltraHorizon benchmark：人类 26.52 vs Agent 14.33
- 标准配置：35k tokens + 60 次工具调用；最大配置：200k tokens + 400 次工具调用
- 56% 的错误来自上下文管理失败，而不是推理能力
- 失败模式在不同任务、不同模型上高度一致
- 来源：S1

**写作目标**：说明这是系统性问题，不是个别 benchmark 的极端情况

---

## 三、直觉解法为什么不管用：上下文窗口更大≠更好

- Vending-Bench 的发现：失败和上下文窗口是否满没有直接相关
- 模型在窗口远未满时就会进入"切线崩溃循环"
- Context Rot（Chroma 研究）：随着输入变长，性能下降不是线性的，是不均匀、不可预测的
- 干扰词的非线性放大效应
- 反推：你给 Agent 1M token 的上下文窗口，它不会因此更稳定
- 来源：S6、S7

**写作目标**：打破"加长窗口就能解决"的工程直觉

---

## 四、真正的原因：上下文锁定

- 精确定义 in-context locking：早期做出的假设或错误判断在上下文里固化，即便后续出现修正信号，模型也无法真正推翻
- 类比：就像你在一张纸上写满了内容，后面的修正意见必须在已有文字的"阴影"下被解读
- 两层机制：
    1. 注意力焦点漂移：随着 token 积累，早期 token 的权重被稀释
    2. 路径依赖：已经生成的 token 约束了后续 token 的分布
- 来源：S1、S7

**写作目标**：给问题一个准确的名字，让读者有"终于讲清楚了"的感觉

---

## 五、反直觉发现：模型需要主动写给自己看

- YC-Bench 的发现：scratchpad 使用是长任务成功率的最强预测变量
- 不用 scratchpad 的模型，即便模型能力更强，也更容易在上下文截断后失去关键信息
- 含义：Agent 的"记忆"不是存在模型参数里的，而必须显式地写出来
- 类比：人类在做复杂计算时，脑子里"记住"远不如在纸上写下来可靠
- 来源：S3

**写作目标**：提供一个有点反直觉但逻辑清晰的实操洞察

---

## 六、现有解法方向

简要介绍三个研究方向，不做产品推荐：

1. **主动上下文管理（Context-Folding）**：Agent 主动决定什么时候分支、什么时候汇总、什么时候"折叠"中间步骤。用 32K token 完成需要
   327K token 的任务。(S4)

2. **任务感知压缩（ACON）**：不是统一截断，而是根据任务目标决定哪些历史值得保留。压缩 26-54% token，不损失性能。(S5)

3. **分段覆写（MemAgent）**：把长文档切成段，用 RL 训练模型决定每段哪些内容值得写入记忆，实现从 8K 到 3.5M token 的外推。(S8)

**写作目标**：说明"问题是可以被解决的"，给读者信心，但不承诺哪个是终极答案

---

## 七、对 Agent 架构设计的含义

- 当前大多数 Agent 框架把上下文管理当成工程优化项，而不是核心设计决策
- 真正稳定的 Agent 需要在架构层就回答：任务历史怎么存、怎么截断、怎么压缩、什么时候重写
- 不解决这个问题，给 Agent 更强的模型、更多工具，成功率上限依然很低
- 来源：S1、S4

**写作目标**：给做 Agent 的人一个思维框架转变

---

## 八、结尾

- 回扣开头：GPT-4 在 TravelPlanner 上 0.6% 的成功率，不是 GPT-4 的问题，是我们还没想清楚 Agent 的记忆结构应该长什么样
- 一句话总结：Agent 不是因为不够聪明而在长任务里失败，而是因为它不会管理自己的注意力
