# 从「人肉对照」到「确定性流水线」：lct-code-review Skill 的演进之路

本文记录 lct-code-review skill 从「一份规范文档 + 人工对照」演进到「脚本兜底 + LLM 判断 + 可量化回归」的完整过程，以及每一步背后的取舍。适合正在做或准备做
AI 工程化落地的同学参考。

## 一、为什么要做这件事

理财通活动中台模块多（活动中台 + 玩法 + 权益三大子系统，30+ 模块）、改动频繁、资金链路敏感。CR 是质量守护的最后一道闸，但人肉
CR 有三个绕不开的痛点：

- **会遗漏**：一个大 MR 几十个文件，人眼扫到后面注意力稀释，核心逻辑文件反而被漏掉。规则全靠脑子记，该查的点总有几个被跳过。
- **精力瓶颈**：团队其他人用 AI 辅助写代码，需求交付速度上来了，MR 产出量激增——结果提效的红利没兑现，瓶颈反而卡在了 CR
  人员身上。CR 的人力带宽成了整条流水线的限速环节。
- **标准不统一**：同一段代码，A 审觉得没问题，B 审判了个严重缺陷。规范虽然有文档，但理解和执行因人而异，CR 质量波动大。甚至同个人不同时间
  CR 结果也不尽相同。

最初的方案很朴素：一份 CR_RULES.md + 人工对照。能用，但上面三个问题一个没解决。

自然的想法是引入 Agent 来做 CR——让 LLM 按照规范审代码。但 Agent CR 并没有一步到位，反而暴露了一组新的问题：

- **看不全**：Agent 会「选择性跳过」文件，自认为不重要的直接略过，覆盖度不可控。
- **看不准**：Agent 发现了问题，但报出的行号是错的，评论关联到无关代码行，作者一脸懵。
- **看不稳**：同一个问题，跑两遍结果不一样；改了 prompt 也不知道是变好还是变差。输出方差大，没有量化手段。

人肉 CR 的问题是「人不够用」，Agent CR 的问题是「用了但不靠谱」。这个 skill 的演进，就是在解决第二组问题的同时，把第一组问题也一并消除。

## 二、演进时间线

### 阶段 0：规范沉淀期（起点）

最早只有一份 CR_RULES.md，把团队规范（命名、订单表设计、单测、事务控制、幂等、金额、敏感信息处理）和 DDD 工程结构规范全塞进去。

这一阶段的核心动作是把隐性共识显性化：

- DDD 分层规范（gateway 层禁止业务决策、PB 对象禁止跨层透传）
- 事务 & 数据源注解规范（@Transactional/@DS 只能加在 Repository Impl，Mapper 类禁止加）
- 工程目录结构标准模板（interface/application/domain/infrastructure 各层职责）

**价值**：规则成文，CR 有据可依。
**局限**：规则全靠人去对照，遗漏/精力瓶颈/标准不统一三个问题原封不动。

### 阶段 1：规范分层期

单一大文件不好维护，也带来「规则噪音」——审一个 Mapper XML 不需要喂 DDD 规则。于是把规范拆成三套：

| 规范文件           | 适用范围                       | 核心内容                                                     |
|----------------|----------------------------|----------------------------------------------------------|
| cr-rules.md    | 所有 MR 必读                   | 通用 Checklist（安全/性能/错误处理/可维护性/测试/兼容性）+ LCT 团队专项 + Java 专项 |
| ddd-rules.md   | gateway/application/domain | DDD 分层职责、核心对象定义、编程公约、工程目录模板                              |
| batch-rules.md | \*-batch / \*Job\*.java    | 批跑专项：单条失败处理、Cursor 流式读取、分片灰度、路由 set 计算、幂等重放、json5 测试     |

并在 SKILL 里加了 Step 1.5 文件类型精细路由：先预扫 diff 文件列表，按 pattern 决定加载哪几套规范，减少无关规则干扰。

**价值**：规则精准投放，降噪。人肉 CR 的遗漏和标准不统一有所缓解，但精力瓶颈问题依然没解——规则再精细，还是得人来看。

到这里，引入 Agent 做 CR 是顺理成章的下一步。但 Agent 一上场，开头提到的三个新问题随即暴露。下一阶段的目标就是治这三个新病。

### 阶段 2：工程化改造期（关键跃迁）

这一阶段借鉴了 [open-code-review](https://github.com/alibaba/open-code-review) 工程的思路，做了一次彻底的「确定性改造」。

**核心心法**（也是整个 skill 的设计哲学）：

> 凡是「不能出错」的步骤（选文件、定位行号、覆盖校验）交给确定性脚本；凡是「需要判断」的步骤（发现问题）才交给 LLM。

LLM 擅长「理解和判断」，但不擅长「精确数数」（数行号、清点文件、保证不遗漏）。把后者从 LLM 手里拿走，三大痛点就从根上被治住了。

落地了 3 个脚本 + 2 类参考资料，逐个对应一个痛点：

#### ① 治「看不全」——gen_checklist.sh + verify_coverage.py

把「决定审哪些文件」的权力从 Agent 手里彻底拿走：

- **gen_checklist.sh**：从 MR changes JSON 机械枚举全部变更文件，按 P1（核心逻辑）/P2（数据层）/P3（配置）/P4（测试）/P5（可跳）分级。Agent
  只能逐项消费这份清单，不得自行取舍，P1+P2 必须 100% 覆盖。
- **verify_coverage.py**：收尾前机械校验必审文件是否全覆盖。返回 FAIL 且有 missing_must 时不得收尾，必须补审后重跑。

一进一出双卡口：入口枚举全量、出口校验闭环，漏审在机制上不可能发生。

#### ② 治「看不准」——locate_line.py

最关键的一条原则：**LLM 只报「问题 + 代码片段原文」，绝不报最终行号。**

行号由脚本反查：接收 (文件路径, 代码片段)，在文件中精确定位真实行号。匹配策略逐级降级（全等 → 忽略空白 → 去全部空白 →
子串包含），坚持「唯一命中」原则——同一片段多处出现且无 hint_line 时判定 ambiguous，宁可不报也不冒险报错位置。

定位不到（not_found/ambiguous）就跳过该评论并在汇总标注，宁可漏报，不可错报。位置漂移从根上消除。

#### ③ 治「看不稳」——review-prompt-template.md + benchmark/

- **结构化 Prompt 模板**：把每次审查指令固化为「固定骨架 + 变量槽」（需求背景 / 规则集 / 文件全文 / diff），LLM 输出严格
  JSON（level/rule/snippet/hint_line/desc）。禁止自由发挥，输出方差大幅下降。
- **基准回归集 benchmark**：把「玄学调 prompt」变成「可量化回归」。每个用例是一段已知答案的历史 MR 片段（ground truth 可靠）。改动
  prompt/规则后跑一遍，对比 Precision（误报）/Recall（漏报），劣化则回滚。这是 open-code-review 工业级 benchmark 的轻量团队版。

#### 配套增强

- Step 1 需求背景注入：从 MR description / TAPD / commit message 提取「为什么改」，避免把符合需求意图的实现误判为问题。
- Step 2.5 文件全文拉取：补全 patch 截断导致的上下文缺失。
- Step 4 同类问题归并：同类问题跨文件 ≥3 次时合并为一条评论，避免「评论轰炸」；单 MR 评论上限 20 条。
- Step 6 复盘自动化：规则命中统计 + 新问题模式沉淀，数据驱动规范迭代。

### 阶段 3：实战打磨期（规则的自我修正）

工程化框架搭好后，靠真实 MR 持续打磨。以下是三个典型案例：

#### 案例一：并发分治规则补丁

SKILL 原本写「文件数 > 5 就起子 Agent 并发审查」。某次 CR 一个 23 文件的批跑 MR 时没有分治。表面看是违反流程，深挖发现：这 23
个文件是单一 Job 的强内聚改动（Job + Partition + WorkerData + Aggregator + Mapper + 测试），审任一文件都依赖其他文件的上下文，拆开反而会丢上下文、导致漏判。

结论是对的（不该拆），但执行错了（没显式声明决策）。根因是规则本身太机械。于是打了补丁：

1. **强制输出「分治决策行」**：无论拆不拆，都要写 `分治决策：文件数=N，<分治/不分治>，理由=...`，杜绝默默跳过。
2. **三档前置判断**：≤5 不分治 / >5 但强内聚不分治（写明理由）/ >5 且弱耦合才分治。
3. **心法定调**：分治边界是「弱耦合」而非「文件数」。文件数只是触发信号，真正决定是否拆的是文件间的上下文依赖强度。

**提炼**：SKILL 规则要给「例外路径」留显式出口，否则 Agent 要么机械执行、要么默默违反。好的规则 = 默认动作 + 例外条件 + 强制声明。

#### 案例二：locate_line.py 匹配策略迭代

最初版本只做全等匹配——LLM 输出的代码片段必须和文件内容字符级完全一致才能命中。上线后发现大量 not_found：LLM 经常在输出时丢掉行尾空格、把
tab 换成空格、或者多缩进一层。这些都不是「报错了」，而是「报对了但格式有微差」，结果全被跳过，漏报率偏高。

于是给匹配策略加了逐级降级：全等 → 忽略行尾空白 → 忽略全部空白差异 → 子串包含。每一级放宽匹配条件，但始终坚守「唯一命中」原则——如果放宽后匹配到多处，宁可判
ambiguous 也不猜。

[待补数据：降级策略上线前后 not_found 率的变化]

**提炼**：「宁缺毋滥」不等于「宁死不报」。在保住精确性底线的前提下，尽可能提高召回。一条错位评论的信任损耗远大于一条漏报，但不必要的漏报同样是损失。

#### 案例三：benchmark 抓住一次 prompt 回归

某次为了减少误报，在 prompt 里加了一条「如果改动是纯重构且不改变行为，降低严重级别」。改完之后人工抽看了几个 MR
觉得效果不错，差点就上线了。跑 benchmark 才发现：回归集里有一个用例是「看似重构实则改变了金额计算精度的 MR」，这条 prompt
改动直接让它从 P1 降成了 P3，漏掉了。

回滚 prompt，针对金额相关改动加了例外条件后重跑 benchmark，Recall 恢复，才正式上线。

[待补数据：该次回归的 Precision/Recall 变化数字]

**提炼**：人工抽检是抽样，benchmark 是全量回归。感觉「好像没问题」和「benchmark 说没问题」是两件事。没有 benchmark 的 prompt
调优就是盲调。

## 三、当前完整工作流

```
Step 1   获取 MR 元数据 + 需求背景注入 + CI 状态检查
Step 1.5 按文件类型精细路由，加载相关规范 + 模块领域文档
Step 2   拉 diff + gen_checklist.sh 机械枚举文件覆盖清单   ← 治看不全（入口）
Step 2.5 拉取改动文件完整内容（补上下文）
Step 3   结构化模板审查 + 并发分治决策                     ← 治看不稳
Step 4   locate_line.py 反查行号 + 同类归并 + 提交评论     ← 治看不准
Step 5   verify_coverage.py 覆盖收尾校验 + 汇总输出        ← 治看不全（出口）
Step 6   规则命中统计 + 新问题模式沉淀（闭环）
```

## 四、方法论：确定性工程 + Agent

上面的演进，本质上不是「CR 专属技巧」，而是一套通用范式。把它抽象出来，可以套用到大量「让 AI 干活但又怕它出错」的场景。

### 4.1 核心矛盾：LLM 的能力边界

LLM（Agent）的能力是有边界的，用错地方就翻车：

| LLM 擅长      | LLM 不擅长        |
|-------------|----------------|
| 理解语义、读懂代码意图 | 精确数数（数行号、清点文件） |
| 发现「这里有问题」   | 保证「一个都不漏」      |
| 判断、推理、生成    | 稳定复现、零方差输出     |
| 处理模糊、灵活的任务  | 严格、确定性的机械操作    |

传统做法是「把整个任务丢给 Agent，再祈祷它别出错」——结果就是覆盖不全、位置漂移、效果不稳。这不是 prompt
没调好，是任务分配错了：把「不能出错」的机械活也交给了概率模型。

### 4.2 范式：把任务拆成「确定性骨架 + Agent 判断点」

核心做法一句话：

> 用确定性脚本搭一条「轨道」，把 Agent 约束在轨道上只做它擅长的判断；凡是不能出错的环节，都用脚本做成卡口，不给 Agent 自由发挥的空间。

拆解成三类角色：

```
┌─────────────────────────────────────────────────────┐
│  确定性脚本（轨道）                                   │
│  - 入口：机械枚举任务范围（不让 Agent 选）            │
│  - 出口：强制校验完成度（不让 Agent 提前收工）        │
│  - 关键事实计算：行号/坐标/数量（不让 Agent 数）      │
└────────────────┬────────────────────────────────────┘
                 │ 喂结构化输入
                 ▼
┌─────────────────────────────────────────────────────┐
│  Agent（判断点）                                      │
│  - 只做「理解 + 判断 + 生成」                         │
│  - 输出结构化结果（JSON），不输出需要精确的事实       │
│  - 用固定 Prompt 骨架约束，降低方差                   │
└────────────────┬────────────────────────────────────┘
                 │ 结构化输出
                 ▼
┌─────────────────────────────────────────────────────┐
│  确定性脚本（兜底 + 校验）                            │
│  - 把 Agent 输出的「片段」反查成「精确事实」          │
│  - 对不上就拒绝（宁缺毋滥）                           │
│  - benchmark 量化效果，回归防劣化                     │
└─────────────────────────────────────────────────────┘
```

### 4.3 五个可迁移的设计动作

这套范式落到任何 Agent 任务上，都对应五个具体动作：

| 设计动作                      | 在 CR 里的体现                        | 解决的通用问题            |
|---------------------------|----------------------------------|--------------------|
| 入口卡口：脚本机械枚举任务范围           | gen_checklist.sh 列全部文件           | Agent 选择性偷懒、覆盖不全   |
| 出口卡口：脚本强制校验完成度            | verify_coverage.py 不全不许收工        | Agent 提前收工、自我感觉良好  |
| 事实外移：精确事实交脚本算             | locate_line.py 反查行号              | Agent 数数/坐标不准、位置漂移 |
| 骨架约束：固定 Prompt 模板 + 结构化输出 | review-prompt-template.md + JSON | Agent 自由发挥、输出方差大   |
| 量化回归：基准集衡量每次改动            | benchmark/ 算 Recall/Precision    | 「调好了没」全凭感觉、改动劣化无感  |

两条从 CR 实战中提炼的补充原则：

- **宁缺毋滥**：行号定位不到就跳过，宁可漏报不可错报。一条错位评论的信任损耗远大于一条漏报。但在保住精确性底线的前提下，要尽可能提高召回（参见阶段
  3 案例二）。
- **规则要留显式出口**：默认动作 + 例外条件 + 强制声明，避免 Agent 机械执行或默默违反（参见阶段 3 案例一）。

### 4.4 可以套用的同类问题

只要任务满足「Agent 来判断，但有不能出错的机械环节」，这套范式都适用：

- **自动化测试生成**：Agent 写用例（判断），脚本跑覆盖率 + 编译校验（卡口），benchmark 是已知 bug 集（量化能不能抓住）。
- **文档/注释自动生成**：脚本枚举所有需补文档的函数（入口卡口），Agent 写内容（判断），脚本校验是否每个都补了（出口卡口）。
- **告警根因分析**：脚本拉全量指标/日志（事实外移，不让 Agent 编数据），Agent 做归因判断，脚本核对结论引用的指标是否真实存在。
- **配置/SQL 审查**：脚本枚举变更项 + 反查精确位置，Agent 判断风险，benchmark 用历史故障做回归。
- **批量数据清洗/打标**：脚本定义范围和校验规则（卡口），Agent 做语义判断，脚本抽样核对 + 量化准确率。

判断一个任务该不该用这套范式，就问三个问题：

1. 这个任务里有没有「数错一个就全错」的机械环节？→ 有，就外移给脚本。
2. Agent 会不会「选择性跳过」或「提前收工」？→ 会，就加入口/出口卡口。
3. 改了 prompt/规则，怎么知道是变好还是变差？→ 建 benchmark。

### 4.5 一句话总结

**不要追求「更聪明的 Agent」，要追求「更可靠的系统」。**

**方法是：把确定性的部分还给工程，把判断的部分留给 Agent，中间用结构化接口对接，两端用卡口和量化兜底。**

## 五、后续方向

- **benchmark 用例扩充**：当前用例偏少，持续把「本该报却漏了」「误报被吐槽」的真实案例补成基准，防回归。
- **规则命中数据反哺规范**：高频命中规则（月命中 ≥5 次）标注加强，长期无命中规则考虑下线。
- **跨模块经验复用**：把通用结论沉淀到 MEMORY.md，让不同模块的 CR 共享判定一致性。
