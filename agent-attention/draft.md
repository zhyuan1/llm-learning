# Agent 的注意力问题：为什么更长的上下文窗口解决不了根本矛盾

---

## 一个让人困惑的数字

Gemini 2.5 Pro 有 1M token 的上下文窗口。在「找针」测试里，从几十万字的文档里定位一句话，准确率接近 100%。这个数字被反复引用，作为长上下文模型已经成熟的证据。

然后把同一个模型放进 SWE-bench，让它解决真实的 GitHub issue。单次长上下文模式下，解决率约 50%。结构化 Agent 工作流（Claude Opus 4.5）在同一基准上达到 80% 以上。

差距依然是 30 个百分点。

一种解释是模型不够聪明，但找针测试已经接近完美，聪明不是问题。另一种解释是任务太难，但同样的模型在 Agent 工作流里能做到 80%，任务也没有变。

真正的问题是：这两个测试考察的不是同一种能力。找针是存储寻址问题，已经被更大的上下文窗口解决了。SWE-bench 是跨多步的推理协调问题，上下文窗口扩大提供的帮助远比直觉预期的少。

把这两个问题混为一谈，是「更大上下文窗口 = 更强 Agent」这个直觉的根源。

---

## 实验说了什么：检索和推理是两回事

Stanford 的 Nelson Liu 等人发表的 *Lost in the Middle: How Language Models Use Long Contexts*（TACL，2023）是这个领域的奠基实验。设计很精巧：把需要检索的信息分别放在上下文的开头、中间、结尾，固定文档总长，只改变关键信息的位置，其他条件完全一致。

结果是一条 U 形曲线：信息在开头或结尾时，模型表现良好；放在中间时，性能显著下降。这个模式在所有测试的模型上都出现了，包括那些明确标榜「为长上下文设计」的版本。更长的上下文不但没改善这个问题，反而让它更明显——20 个文档时的中间位置性能，比 10 个文档时更差。Chroma 2025 年对 GPT-4.1、Claude Opus 4、Gemini 2.5 等 18 款前沿模型的系统复测证实：U 形曲线在最新模型上依然成立。

这个实验测的是什么：不是模型能否处理长文档，而是模型能否**可靠地使用**长文档里特定位置的信息。结论不是「放不下」，而是「用不好」。

这个区别切断了「更大的窗口 → 看到更多信息 → Agent 更强」这条推理链。模型确实看到了所有信息，但不是所有位置的信息都能获得足够的注意力权重，在推理中产生实质影响。

Adobe Research 的 NoLiMa 基准（arXiv:2502.05167，2025）进一步拆解了这个问题。它专门测试**非词汇匹配**的检索，即「针」和「草堆」没有字面上的字符串重叠，必须靠语义推理才能找到关联：

| 模型 | 1K tokens | 8K tokens | 32K tokens |
|------|-----------|-----------|------------|
| GPT-4o | 99.3% | 89.2% | 69.7% |
| Claude 3.5 Sonnet | 85.4% | 61.7% | 29.8% |
| Llama-3.3-70B | 91.0% | 62.7% | 43.2% |

（注：论文原始测试数据，模型为 2024 年底版本）

13 个被测模型中，11 个在 32K token 时跌到短上下文基准的 50% 以下，包括专门做了推理优化的 DeepSeek-R1。NoLiMa 揭示了一个关键分界：词汇相似度高的任务（needle 和 haystack 字面相关），扩容有效；词汇相似度低的任务（需要语义关联才能找到连接），扩容几乎无效。真实 Agent 任务里，需要的往往是后者。

Chroma 的 Context Rot 测试（2025）覆盖了 GPT-4.1、Claude 4 系列、Gemini 2.5、Qwen3 等 18 款模型，结论是：**10K token 是新的失效临界点**。超过这个阈值，大多数模型准确率跌到约 50%，无论初始能力多强。失效是悬崖式的，不是线性渐进的——Claude Sonnet 4 在 1K token 时接近满分，过了 1K 就急剧跳水。干扰项效应尤其突出：加入 1 个干扰项，准确率下降 10-15 个百分点；加入 4 个，下降 30-50 个百分点。更出乎意料的是，**结构连贯的文本比随机打乱的文本表现更差**，模型更容易被连贯叙事带偏，跟着逻辑走而不是锁定目标信息。

SWE-bench 的数据最能说明问题。暴力长上下文模式和结构化 Agent 工作流的差距，过去几年从未因为上下文窗口扩大而消失：早期差距是数倍，今天 Gemini-2.5-Pro 的长上下文模式约 50%，结构化 Agent（Claude Opus 4.5）在同一基准上超过 80%。差距不是缩小了，绝对值反而变大了。两种模式任务相同、底层模型能力相近，区别只在于信息呈现的方式。上下文窗口从 32K 扩展到 1M，没有缩短这个距离。

WebAgent 的 2025 年评测（arXiv:2512.04307）测试了 Claude-3.7、GPT-4.1、Llama 4、o4-mini 在真实网页操作任务上的表现：短上下文下成功率 40-50%，上下文超过 25K-150K token 后成功率跌到 10% 以下。失败的首要模式不是给出错误答案，而是 GPT-4.1 进入循环的频率高达 44.29%，Agent 失去任务连贯性，在某个局部反复尝试，忘记了它在做什么。

## 为什么会这样：机制

### Softmax 是零和博弈

自注意力的计算过程是：对序列中的每个 token，计算它和所有其他 token 的相关性分数（通过 Query 和 Key 的点积），然后对这些分数做 softmax 归一化，得到注意力权重分布，再用这个分布加权求和所有 token 的 Value，作为当前 token 的表示。

关键在 softmax：它要求所有位置的权重之和严格等于 1。这是一个零和约束。上下文里多一个 token，这个 token 就加入竞争，其他所有 token 分到的平均权重就相应减少。

用数字来说：
- 1000 个 token：每个 token 平均权重 0.1%
- 10 万个 token：每个 token 平均权重 0.001%
- 100 万个 token：每个 token 平均权重 0.0001%

这不是工程实现问题，是数学。只要使用任何形式的归一化注意力，这个约束就存在。

### Attention Sink：首 token 吸走了近一半的预算

实际推理中，注意力权重的分配并不均匀，而是极度倾斜。模型会把约 46% 的注意力权重集中到序列的第一个 token 上，通常是 `<bos>`（序列开始标记）或系统提示的第一个词，哪怕那个 token 和当前推理完全无关。

这个现象叫 Attention Sink，成因可以从两个层面解释。

**数学层面：** softmax 在处理全局低相关度的情况时，必须把注意力预算倾倒到某处。当序列里没有高度相关的 token 时，softmax 会把剩余权重分配给最稳定的锚点，而首 token 由于始终在序列开头，在大量不同场景的训练里积累了作为锚点的稳定性，成了模型「不知道关注什么」时的默认去处。

**训练动态层面：** 自回归训练要求模型预测下一个 token，首 token 在这个过程里承担了维持梯度稳定流动的功能，通过把高注意力权重集中在它身上，深层 Transformer 避免了表示坍塌（representation collapse）。这个机制是训练中自然涌现的，不是人为设计的，但副作用是首 token 在推理时持续充当注意力的黑洞。

Qwen 团队在 NeurIPS 2025 提出的 Gated Attention，通过门控主动抑制这个效应，将首 token 的注意力占比从 46.7% 压低到 4.8%。这不是在修一个偶然出现的 bug，而是在对抗一个深度嵌入训练动态的系统性偏向。

### RoPE 的近端偏好

主流模型（LLaMA、Mistral、Claude、GPT-4 等）普遍使用旋转位置编码（RoPE）。RoPE 通过旋转 Query 和 Key 的向量表示来编码位置，旋转角度随 token 之间的距离增大，使得注意力权重随距离指数衰减。

短序列里这是好设计，让模型重点关注附近的上下文，符合语言的局部依赖性质。但在需要跨大距离激活信息的 Agent 任务里，这个性质成了障碍：初始指令和最近的工具返回结果之间可能相隔几万个 token，注意力权重衰减到可以忽略不计的程度。

### 三个效应叠加的结果

把零和约束、Attention Sink 和 RoPE 的近端偏好叠加在一起：

- **开头**：靠首 token 效应维持可见性，序列中所有后续 token 都能回看开头，在自回归训练里积累了较高的基础注意力权重
- **结尾**：靠近端偏好维持可见性，距离当前预测位置最近，天然获得较高权重
- **中间**：两头都不靠，既没有首 token 效应，也没有近端优势，在注意力竞争中持续处于劣势

序列越长，中间区域的相对劣势越大。U 形曲线不只是经验观察，而是从架构性质可以预测的结果。

这些机制不是训练失误，不是调参能修复的问题。它们根植于 Transformer 的基本工作原理：因果掩码、softmax 归一化、旋转位置编码。要从根本上改变这个格局，需要改变架构，不是改变上下文长度。

## 无限上下文能解决问题吗

一个合理的反驳是：既然问题来自中间信息被稀释，那如果能实现真正「无限」的上下文窗口，问题是不是就消失了？

先承认一个事实：对于简单的单点检索，扩容确实几乎解决了问题。Gemini 在 1M token 上下文下做 needle-in-haystack，准确率接近 100%。如果你的问题是从超长文档里捞一句话，更大的窗口的确有效。Needle-in-haystack 里的那根「针」，只要被放进上下文，softmax 就能通过足够强的局部相关信号找到它，因为这根针和问题之间的语义匹配度极高，足以在注意力竞争中脱颖而出。

但切换到需要综合多个事实推理的任务，情况就变了。同样是 Gemini，在 MRCR（需要跨多个位置同时检索多个相关事实）基准上：128K 上下文下准确率 91.5%，扩展到 1M 之后降到 83.1%。窗口扩大了将近 8 倍，性能反而下降了近 10 个点。多针问题里每根针的相关信号强度分散了，所有位置的信号被均匀稀释后，模型就更难同时激活所有需要的信息。

**这里有一个数学上的根本约束。** 研究（arXiv:2508.17821）从理论上证明：对于任何使用平滑归一化函数（包括 softmax）的注意力机制，序列中任意 token 的最大注意力权重存在理论上界 O(1/L)，其中 L 是序列长度：

```
C₁/L ≤ αᵢ ≤ C₂/L
```

不管信息多重要，随着序列增长，它能获得的最大注意力权重上限随序列长度线性递减。L 趋向无穷大时，αᵢ 趋向零。无限上下文不会让模型更聚焦，只会让注意力稀释得无限薄，直到模型无法区分任何信息的优先级。这是数学证明，不是经验观察。只要保留 softmax 归一化这个设计，就无法逃脱这个约束。

**认知科学有一个有帮助的参照。** Miller's Law 指出，人类工作记忆容量约为 7±2 个信息块，与长期记忆的大小完全无关。人类长期记忆的容量几乎无限，但没有人会说「读更多书就能让你同时思考更多事情」。工作记忆容量是神经系统并发处理能力的限制，不是存储容量的限制。扩大「硬盘」（长期记忆）对「RAM」（工作记忆）没有帮助，因为它们是两个正交的维度。对 Transformer 注意力机制的 n-back 任务研究（arXiv:2409.10715）发现了类似的模式：随着任务要求的回溯深度增大，模型注意力分数熵增加，性能下降。Transformer 的注意力机制同样受到类似工作记忆的约束，有效并发激活的信息量有上限，且这个上限与上下文窗口大小关系不大。

**SSM 架构的教训进一步说明了问题的本质。** Mamba 等状态空间模型（SSM）把注意力的时间复杂度从 O(n²) 降到 O(n)，使得无限上下文在计算上变得可行。但 SSM 解决计算成本的方式，是通过维护一个固定大小的隐藏状态来压缩历史信息，每一步把当前输入和历史状态合并成新状态。遥远的历史信息以指数速度衰减，直到其影响趋近于零。这不是 bug，是 SSM 能达到线性时间复杂度的根本原因——如果要完整保留所有历史信息，状态就必须随序列增长而增大，复杂度就回到了线性甚至以上。

结果是：Transformer 把「中间区域信息被忽视」换成了「久远历史信息被遗忘」。两种形态不同，但对 Agent 的影响是一样的——任务开头的目标约束，无论是在 Transformer 的中间区域，还是在 SSM 的远古历史里，都无法在任务全程保持可靠的激活强度。即使计算成本问题被解决了，Agent 对跨任意步骤可靠激活关键信息的需求，仍然没有被满足。

## 根本矛盾

Transformer 的每次前向传播是无状态的：给定上下文，对所有位置重新计算注意力权重，生成输出，完成。没有任何信息天然地从上一次推理「延续」到下一次，每次都是从头竞争。上下文窗口里的所有内容，在每次推理时都处于平等竞争的状态，都要服从 softmax 的归一化约束。

单次推理任务里这完全没问题。给模型一篇文章，问一个问题，模型从头算一遍注意力，输出答案，结束。

Agent 任务完全不同。一个复杂的编程任务可能包含：理解任务描述（初始上下文）、读取相关文件（工具调用 × N）、分析代码结构（推理步骤 × N）、写代码、测试、调试（工具调用 × N），以及在整个过程中持续遵守任务的初始约束。每一步都产生输出，这些输出作为新的上下文进入下一步。经过 50 步之后，上下文里可能已经堆积了几十次工具调用的返回结果、多轮中间推理、部分代码草稿——它们全都参与每次的注意力竞争。而任务在第 1 步定义的目标约束（「不要修改测试文件」「保持向后兼容」），注意力权重随着上下文的堆积在每一步都在缩小。

**上下文扩容解决的是装载容量（能放多少信息进去），Agent 需要的是跨步骤的可靠激活（初始目标在任务全程都能被充分注意到）。** 给更多空间，只会让更多后续内容进来稀释初始信号。噪声增加，信噪比下降。

Anthropic 在工程博客里把这个现象直接叫做「context rot」，并承认「模型在更长的上下文下依然有能力，但可能表现出精度下降」。他们的解法不是把窗口做得更大，而是「管理放进窗口里的内容」：压缩历史、维护结构化笔记、按需检索。做模型的人自己，在工程实践里也是靠精准控制窗口里有什么，而不是靠扩大窗口。

当上下文利用率超过窗口容量约 40% 时，Agent 性能会出现急剧下降，不是线性退化——不是「用的越多，性能慢慢变差」，而是「超过某个点，性能会突然跳水」。对于构建可靠系统来说，这个特征比线性退化更危险，因为失败来得悄无声息，没有溢出报错，没有明显的性能曲线预警。

另一个角度的数据：一个 34B 参数的模型在 100K token 上下文下，大约只能支持 5 个并发用户，KV cache 消耗约 22.8 GB；在 4K token 上下文下，可以支持 100 个以上并发用户，KV cache 只有 0.91 GB。成本增加了二十五倍，能力却变差了。

SWE-Pruner（arXiv:2601.16746，上交大+字节跳动，2026）给出了一个更精确的数字：SWE-bench 真实任务里，**76.1% 的 token 消耗来自文件读取操作**，而这些内容大部分与当前步骤的直接需求并不相关。通过动态剪枝，只保留语义相关内容，token 使用量减少 23-54%，任务成功率下降不足 1%；在「失败→成功」对比场景里可节省 83.3% 的 token。这不是在压缩信息，而是在过滤噪声——这些噪声原本都在参与每步的注意力竞争，系统性地拉低了有用信息的有效权重。在错误的维度上扩容，不只是没有帮助，是在用更多的钱买更差的结果。

## 三个具体的失效模式

**目标漂移（Goal Drift）**

一个 Agent 被委托完成这样的任务：「审查这份合同，找出所有不符合我们公司政策的条款，特别注意知识产权归属的部分。」

Agent 开始工作：读合同、搜索相关政策文件、比对条款、标记问题……经过二三十步之后，上下文里已经堆满了合同文本片段、政策摘录、中间分析结论。「特别注意知识产权归属」这个约束，在注意力竞争中的份额越来越小，而最近读到的「竞业禁止条款」因为离当前位置近，主导了模型的注意力。Agent 开始深入分析竞业禁止，忘记了它最初被要求重点审查的是知识产权归属。

这不是 Agent 在主动违背指令，而是在一步步做「局部合理」的事情，但初始约束的注意力权重随上下文增长持续衰减，全局目标悄悄地被稀释了。

专门研究这个问题的实验（arXiv:2505.02709）把 Agent 放在模拟股票交易环境里，给定明确的投资约束（如「最小化碳排放」），然后让它执行长期任务。结果是所有被测试的主流模型都在长时间运行中出现了目标漂移。漂移的主要模式不是「主动违背目标」，而是「通过不作为偏离」——Agent 没有反过来做高碳排放的决策，但随着上下文增长，它越来越少地把「碳排放」这个约束纳入每步决策。它没有忘记这个目标，但这个目标在注意力竞争中的权重已经低到无法持续影响行为。

**上下文污染（Context Pollution）**

Agent 在第 8 步做了一个错误的中间判断：「这个 bug 是由模块 A 引起的。」基于这个判断，它花了接下来的 15 步深入分析模块 A，积累了大量关于模块 A 的上下文。到第 23 步，有新的证据出现，表明 bug 实际上来自模块 B。

问题是：之前 15 步关于模块 A 的分析都还在上下文里，数量远超关于模块 B 的信息。每次前向传播都要处理这些内容，而它们和关于模块 B 的新证据共享同一个注意力预算。「模块 A」的关键词频率更高，占用的 token 数量更多，这会系统性地把注意力权重拉向模块 A。Agent 可能看到了关于模块 B 的新证据，但这个信号被淹没在更庞大的模块 A 分析语料里。

更深的问题是：错误推理一旦进入上下文，就没有标注来区分它和正确推理。模型不知道「第 8 步的判断是错的」，因为上下文本身没有这个元信息。错误以复合方式积累：第 8 步的错误影响第 23 步，第 23 步在错误基础上做的推理影响第 40 步，到任务后期往往已经无法从上下文内部纠正，因为整个推理链都是在错误的初始判断上构建的。

**工具调用退化（Tool-Use Degradation）**

Anthropic 工程师总结了一个判断标准：「如果人类工程师自己都无法清楚说出应该用哪个工具，Agent 同样会困惑。」随着上下文增长，工具选择的准确率系统性地下降。工具定义通常放在上下文的靠前位置（系统提示里），随着后续内容的堆积，这些定义获得的注意力权重持续减小；多次工具调用的返回结果里，往往包含大量与当前步骤不直接相关的内容，它们和工具定义竞争注意力，进一步稀释模型对工具能力边界的清晰认知。

SWE-bench 里一个典型的失败模式：任务需要同时修改 5 个文件，这些文件之间有数据流依赖关系（一个数据结构定义、两个使用它的函数、一个测试文件、一个配置文件）。Agent 在短上下文模式下，每步只处理当前相关文件，跨文件的依赖关系清晰可见。但在长上下文模式下，5 个文件的内容都在上下文里，文件间依赖关系的信号被大量无关代码稀释，Agent 最终只修改了其中一个文件，然后停下来报告完成。不是它不知道其他文件需要修改，而是那些关联信息的注意力权重已经低到无法有效激活跨文件的修改动机。

## 真正有效的方向

所有真正有效的方案，都在做同一件事：把「存储」和「激活」分开处理，让上下文窗口在任意时刻只保留当前步骤实际需要的信息。

### 管理层面：用显式设计代替被动稀释

**MemGPT（Letta）的操作系统类比**

UC Berkeley 开发的 MemGPT（现已演化为 Letta 框架）直接用操作系统内存管理的逻辑来解决这个问题。系统把内存分成两层：主上下文（对应 RAM）和外部存储（对应硬盘）。主上下文里只放当前步骤实际需要的信息，其余信息存在外部存储里。Agent 自己负责决定何时把什么信息分页进主上下文，何时把不再需要的信息写回外部存储。

这个设计把「什么时候激活什么信息」这个决策从模型的隐式注意力机制里分离出来，变成显式的可编程行为。注意力机制本来是在做这件事，但它做得不可靠，受到各种结构性偏向的干扰。MemGPT 把这个决策拉出来，让它变得可控和可审计。实验结果：文档处理能力提升 10 倍，对话一致性提高 41%——底层模型完全没有变。

MemGPT 的思路在 2025 年被推进了一步。字节跳动和清华大学联合发布的 MemAgent（arXiv:2507.02259）用强化学习训练一个专门负责内存管理的子 Agent：把文档切成小块，用 RL 学习「哪些内容值得写进记忆缓冲区、哪些可以丢弃」，靠任务反馈自动学会取舍。结果是在 RULER 基准 512K token 长度下超过 95% 的准确率，从 8K token 的训练上下文外推到 350 万 token 的任务时，性能下降不足 5%。模型从来没有见过那么长的上下文，但因为它学会了管理注意力而不是依赖窗口容量，外推能力远超预期。

**GraphReader 的反直觉证明**

GraphReader（arXiv:2406.14550，2024）用只有 4K token 上下文窗口的模型处理长达 256K token 的文档，在需要复杂推理的 LV-Eval 基准上击败了 GPT-4-128K。

做法是：不把文档直接塞进上下文，而是先把文档转化成知识图谱，把关键实体和事件作为节点，它们之间的关系作为边，然后让 Agent 通过遍历图节点来回答问题：先确定与问题相关的入口节点，沿着相关的边扩展，读取每个节点的详细内容（只在需要时加载），记录发现的关键信息，直到收集到足够回答问题的证据。

图遍历根本不存在「中间信息被遗忘」的问题，因为它根本就没有「中间」——每次遍历步骤，当前节点就在上下文的最近位置，权重最高；需要回看的节点随时可以重新加载，不存在被长距离衰减稀释的问题。每步只处理和当前推理直接相关的图节点，没有任何无关内容在竞争注意力。

**Chain-of-Agents 的分治策略**

Google Research 的 Chain-of-Agents（CoA）框架（arXiv:2406.02818）把长任务拆分后分配给多个 Worker Agent，每个 Worker 只处理一段短文本，处理完后把关键发现传递给下一个 Worker 或汇总给 Manager Agent。每个 Worker 的上下文里只有它负责的那段文本，加上前一个 Worker 的摘要性传递，没有无关内容，注意力预算全部集中在有效信息上。

复杂度从 O(n²) 降到 O(nk)（k 是每个 Worker 的上下文大小），在 MuSiQue（多跳问答）和 NarrativeQA（叙事理解）上比完整上下文方法分别高出 10.22% 和 13.30%。不是因为 Worker 更聪明，而是因为每个 Worker 都在高信噪比的环境里工作。

**Anthropic 的工程实践**

Anthropic 在构建 Claude Code 等产品时形成的上下文管理实践，逻辑和上述研究完全一致：

- **压缩（Compaction）：** 上下文接近窗口上限时，把对话历史总结成关键决策和未解决问题，丢弃中间的冗余输出。不是因为信息不重要，而是因为把所有历史细节保留在上下文里，增加的噪声超过了增加的信号，对后续推理的净贡献是负的。
- **结构化笔记（NOTES.md）：** 让 Agent 维护一个外部文件作为持久化状态，把跨步骤需要追踪的关键信息显式写入，每步推理时重新加载。这是在手动实现 MemGPT 的分页机制，只是用文件系统代替了向量数据库。
- **即时检索（Just-in-time Retrieval）：** 不在任务开始时把所有可能相关的信息预加载进上下文，而是在实际需要某个信息时再去检索，让上下文在任意时刻只包含当前步骤真正需要的内容。

### 架构层面：降低成本，但问题的性质没有改变

FlashAttention、稀疏注意力、KV Cache 压缩等技术解决的是 O(n²) 计算成本的问题。FlashAttention-2 通过 GPU 内存层次结构的重新组织，把内存访问从 O(n²) 降到 O(n)，使得更长的上下文在硬件上变得可行。稀疏注意力（如 MInference）在 A100 上实现了约 10 倍的预填充加速。DeepSeek-V3 的 Dynamic Sparse Attention 把 16K token 序列的 GPU 内存消耗降低了 65%。

这些技术是重要的基础设施，没有它们，上述管理层方案的成本高得无法大规模部署。但它们本身不解决注意力质量问题——更快、更便宜地处理长上下文，不改变 softmax 归一化的零和约束，不改变 Attention Sink，不改变 RoPE 的近端偏好。它们让你更便宜地把问题重复一遍。

真正的进展需要两层结合：架构层降低成本，让工程上可行；管理层提升质量，解决注意力稀释的根本问题。单独用架构层优化，等于花更少的钱做一件同样错误的事情。

## 结语

Karpathy 有个常被引用的类比：LLM 是 CPU，上下文窗口是 RAM，API 调用是系统调用。在这个框架里，Agent 架构扮演的是操作系统的角色，决定什么时候把什么信息加载进工作内存，什么时候清空，什么时候换入新的内容。

没有人会说「更大的 RAM 能让操作系统变聪明」。RAM 越大当然有帮助，但帮助的是操作系统能同时调度更多进程，而不是让任何单个任务的处理变得更精准。操作系统的核心能力是调度：在任意时刻，把最需要的东西放在最快的地方，把不需要的东西换出去腾出空间。调度策略糟糕的操作系统，给再多 RAM 也只会浪费在缓存里的过期页面上。

Agent 的注意力问题是同构的。模型在每一步前向传播里能有效处理的信息密度，受到 softmax 归一化的数学约束，不因窗口大小改变。窗口越大，如果没有主动管理，稀释的只会更均匀。GraphReader 用 4K 上下文打败 GPT-4-128K，是最直接的证明：当信噪比足够高时，少量上下文比大量上下文更有效。

这并不是说上下文窗口的扩大没有价值。对于简单检索任务，它确实解决了问题；对于减少分页次数，它确实降低了系统复杂度；作为架构层优化的基础设施，它让更多管理层方案变得可行。但「更大的窗口」和「更强的 Agent」不是同一回事，在当前的 Transformer 架构下，前者对后者的贡献比大多数人想象的要有限得多。

真正困难的问题，是如何在任意步骤让 Agent 可靠地激活它此刻最需要的信息——这需要被设计进系统架构里，可能是显式的外部记忆、可能是分层的 Agent 结构、可能是状态外置的目标追踪，但不会靠堆叠更多 token 自然涌现出来。

「给更多上下文」是个诱人的解法，因为它简单：改一个数字，钱多花一点。但它解决的始终是存储问题。注意力的问题，只能靠管理注意力来解决。
